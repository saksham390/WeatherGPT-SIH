# WeatherGPT Interview Notes

This document describes only implemented features.

## Implemented answers

The application is a modular monolith: one Spring Boot backend and one React frontend. The backend owns provider and AI secrets; the frontend calls backend endpoints through the Vite development proxy.

### Why LangChain4j?

LangChain4j provides the Java-native AI Service abstraction, tool calling, chat memory, embeddings, and retrieval integration used here. `WeatherAssistant` is backed by Gemini only when explicitly enabled.

### What is Tool Calling here?

`WeatherTools` exposes `@Tool` methods backed by `WeatherService`. Gemini can request current weather, forecasts, or deterministic alerts; Java executes the method and returns structured data for the final answer.

### What is RAG here?

Markdown safety and agriculture documents are split, embedded with Gemini embeddings, stored in pgvector, and searched through LangChain4j's `EmbeddingStoreContentRetriever`. Retrieved chunks become context for the AI Service.

### Why is the alert engine deterministic?

Weather warnings are generated by configured thresholds in `WeatherService`, not invented by the model. Gemini can explain an alert, but it cannot create the underlying rule-based fact.

### How is failure handled?

Without `GEMINI_ENABLED=true`, `/api/chat` returns an explicit capability message. Weather remains available through the mock provider and is labeled `demoData=true`. Invalid weather inputs return HTTP 400 through centralized exception handling.
